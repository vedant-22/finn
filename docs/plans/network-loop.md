# network-loop: the Network changes Today and closes its loop

Stage: done 14 Nov. Model: opus. Read with `docs/CONTEXT.md` (the rules that keep the Network honest) and `docs/plans/notice.md`.

## Plan v1 (14 Nov)

### Goal and what "done" means
The brief's last word on the Network is "show us what it notices that the investor wouldn't". `notice` built the joins; they still sit in a fold, the investor can't answer the one question the Network asks them, the people it names don't always fit the question beside them, and five invented profiles still feed real people's careers. Done means:

1. **Real people carry only filed fields.** `data/network/profiles.json` and the code that attaches it are gone. Every line about a person in a filing is unchanged or more honest, measured by a diff, not assumed.
2. **The investor can answer "Is it the same person?"** with Yes or No where it is asked. The answer stays on the phone, every view rebuilds from it, and it can be changed.
3. **A notice with no filing of its own can raise a card on Today**: at most one, finishable like any card.
4. **The person beside a question fits the question.** "Ask first" on Today's end band is chosen by what the question is about. A quarterly result is no longer a reason to call anyone.

Every rule in `docs/CONTEXT.md` ("The rules that keep it honest") still holds and is still asserted.

### 2. Yes or No on a name it can't place
**Where.** Everywhere FINN asks "Is it the same person?" or says "This may be the X you know": the notice in "From your network", the note in a card's full view, and the company page. One small component, two buttons: "Yes, it's them" and "No, someone else". After an answer the line reads as the engine words it ("This is the Jigar Shah you know. You confirmed this.") with "Change" beside it.

**How it rebuilds.** Options:
| Option | Verdict |
|---|---|
| A. The phone sends its answers with one request; `/api/network` op `views` rebuilds notices, filing blocks and company views from them and returns the same shape as `network.json`; nothing is stored on the server | **Chosen.** The engine stays the one place the joins are made; the answer stays on the phone |
| B. Patch the static file in the browser (hide the question, reword the note) | Rejected: a Yes changes joins (Jigar is now inside HDFC Bank, so never asked a question and never a pattern's person); patched copy would be faked output |
| C. Precompute both answers into `network.json` | Rejected: doubles per question, and answers interact |
| D. Store answers on the server | Rejected: needs accounts, and breaks "stays on the phone" |

**Details.** Answers live in `localStorage` (`finn.identity`, `{"<person>|<contact>": "same"|"different"}`). With no answers the app uses the static file as now. With answers it shows the static file at once, then swaps in the rebuilt views; the rebuilt views are cached on the phone keyed by snapshot date and answers, so the next open is instant. The API applies an answer only to a pair the engine marked "possible" (already true in `Network.__init__`), keeps the existing caps (200 answers, 64 KB body, keys cut at 120 characters), and returns 400 for a malformed body. If the server can't be reached the answer is still saved and the line says so: "Saved on this phone. FINN will apply it when it can reach the server." A pair that no longer exists in a newer snapshot is ignored.

**Checks.** Engine: Yes on Jigar gives the "contact" notice and removes the question; No removes the question and the note reads "You said this is someone else."; Jigar is never asked a question or pinned after a Yes; an answer about a pair the engine didn't ask about leaves every view byte-identical. API: `op: views` returns the three keys, rejects a non-object, honours the caps. Security: the answers are not logged or written anywhere (grep the handler; check no file is written during a request). e2e: Month window, answer Yes in the fold, the fold now says "Jigar Shah, who you know, has joined HDFC Bank as General Counsel."; reload keeps it; Change and No restores the static wording.

### 3. A notice can raise a card
**Which.** The engine marks a notice `card: true` when it is a join across two or more filings that Push cannot see filing by filing, and it names one contact with a question: today that is **control seats** and **one call, two answers**. Everything else stays in the fold. Today shows at most one such card in a window, chosen as the fold already ranks (patterns first, then one call), dated inside the window. On the 28 Oct snapshot: the 24-hour window gains "One call, two answers" (Meera Krishnan; Home First's new CFO and HDFC Bank's new MD & CEO; 27 Oct); the month gains Crompton's control seats (16 Oct).

**The card** (Folio's card grammar, `DESIGN.md`): the chip "Your network"; the name in the book serif (the contact for one call, the company for control seats); one sentence (the notice's line); no price strip; the demo label. Read more opens a full view built from what the engine already computes: for one call, each company's clause and its question, when you last spoke, and "Copy the call sheet"; for control seats, the filed evidence, the one person and question, the question for the next call, and a link to the company. Keep and Clear work as on any card; Listen reads it. A raised notice leaves the fold, so nothing is said twice. A network card raises no phone notification: it crossed none of the investor's lines, and Push notifies only on those.

**What changes on screen.** The 24-hour brief reads "3 need you" with the third card Meera's; the walkthrough's first beat and its checks move with it.

**Implementation.** `buildBrief(push, lines, raised?)` takes the in-window card notices; an `Item` gains `kind: 'network'` and `notice`. The key is `net|<kind>|<at>|<contact>`, so Keep and Clear survive a reload and a rebuild. The full view is a new branch in `Reader.tsx` that reuses `PathView`'s call-sheet copy and `Patterns`. Unit tests in `web/test/stage4.test.mjs`: one card at most, none outside the window, the key is stable, a raised notice is not in the fold, no notification.

Rejected: every notice a card (a feed); promoting the fold's first row (it doesn't change what the brief asks of the investor, and can't be finished).

### 4. The person fits the question
**"Ask first"** on the end band. Each row's question has a kind, known where it is made (`newsQuestion` in `queue.ts`): **a departure** ("Why did the CFO, Deepak Jain, leave…?") or **the numbers** (a margin or profit question, or the ledger's question for the next call, which is about guidance). The engine gives each company view `ask_first: {leave, numbers}`, each a contact with its line, or null:
- **leave**: someone who worked inside the company and has left (their years printed; nobody inside it now, nobody who left within the year, as today).
- **numbers**: someone who sees the business now from a seat that bears on results: at a competitor, customer or supplier today. Nobody who has left knows this year's numbers, and a group colleague sees the group, not the quarter.
- If neither fits, the row has no "Ask first". Silence is shown, not filled.
- If the contact chosen is pinned on a path at that company, the row prints the path's question for them in place of the generic line, so a person carries one question everywhere.

On the snapshot: Syngene's departure row keeps Dr. Leena Joshi; L&T's margin row keeps Anand Raghavan (Tata Projects); Home First's guidance row changes from Kavita Deshmukh (left in 2020) to Meera Krishnan (CFO at Aavas Financiers today), printed with her question from Rinkoo's path if the path pins her; HDFC Bank's row loses Neha Saxena (same group).

**A reason to call.** `warm()` stops counting a results filing as a reason: a quarter's results come on the calendar, not because of the contact. What remains: the contact named in a filing, or a material non-results event in their line of work. The count of reasons falls; that is the point. Checked: no reason's filing is a results filing; the count is asserted.

Rejected: matching a contact's old division to promise topics in the ledger (word matching; `notice` measured this noise on themes, and the ledger's evidence comes from calls, so "settled by these results" can't be known).

### Risks and how each is handled
| Risk | Handling |
|---|---|
| A rebuild on Vercel is slower than 2.7 s, or times out | Measure on the live link; the static view shows meanwhile; if it is over 5 s, rebuild only the views that name the person, the contact or their companies |
| The new op is a CPU lever for abuse | Only answers about pairs the engine asked about trigger a rebuild; otherwise the cached base views are returned. The firewall rate rule in `NEEDS_FROM_USER.md` covers it |
| Keep or Clear lost when a card's content changes after a Yes | The key is the notice's kind, date and contact, not its words |
| A third card makes the 24-hour brief busier | One network card at most; it is the one join of the day; the fold keeps the rest |
| The diff hides a change | The with/without diff is rerun after the change and every remaining difference is listed in the execution log |
| A pronoun or a word of suspicion in new copy | New copy is a few fixed strings; the existing check over every notice and path covers the new fields |
| Docs drift | `claims.py` gets the new counts; README, covering note, walkthrough, brief trace, `ARCHITECTURE.md`, `NETWORK_CORE.md`, `DESIGN.md`, `DECISIONS.md`, `CONTEXT.md` updated before done |
